# Changes on top of upstream

> These pages hold the Lake.Parquet fork's decisions; the fork ([rtkelly-labs/parquet-dotnet](https://github.com/rtkelly-labs/parquet-dotnet)) carries the code
> and one change record per change. Paths in `code` are paths in the fork.

Lake.Parquet is [aloneguid/parquet-dotnet](https://github.com/aloneguid/parquet-dotnet)'s `master`,
unchanged, with a stack of commits on top: one per change, each with a record in this directory.
This page is the rules for that stack; the tool that keeps it is [`eng/lake/Lake.Stack`](https://github.com/rtkelly-labs/parquet-dotnet/tree/master/eng/lake/Lake.Stack)
(`lake-stack` below; [`../maintaining.md`](maintaining.md) has how to run it).

The point is to know at any moment exactly what Lake.Parquet adds to upstream, and to drop each
addition once upstream has it.

## The stack

```text
upstream/master ── 0001 ── 0002 ── 0003 ── ... ── 0025      = master
                   │       └ one commit per change, with its record
                   └ packaging, CI and these docs
```

- **Upstream's commits are never rewritten.** They are in `master` with upstream's hashes, and
  `git merge-base master upstream/master` is always the upstream commit Lake.Parquet is built on.
- **Each change is exactly one commit**, `lake(NNNN): title`, which adds or edits its record
  `NNNN-name.md` together with the code. `git show` of that commit is the whole change.
- **No merge commits above upstream.** The stack is linear, so it can always be rebased.
- **The stack is rebaselined onto upstream, never merged**, when the maintainer decides to
  (`lake-stack rebaseline`, [`../maintaining.md`](maintaining.md)).

commitlint (`commitlint.config.mjs`) checks every commit subject and pull request title, and `lake-stack check` enforces the first three, and CI runs it on every push and pull request.

## Record format

`NNNN-short-name.md`, numbered in stack order, with YAML frontmatter:

```yaml
---
title: "Exact decimals for INT32/INT64-backed columns"
kind: code                 # addition (fork-only files) | code (changes upstream's code)
status: fork-only          # fork-only | proposed-upstream | upstreamed | superseded
depends_on: [0008]         # changes below it that it needs, or overlaps line for line
upstream: https://github.com/aloneguid/parquet-dotnet/issues/...   # optional; any issue or PR, ours or not
evidence: failing-test     # optional: failing-test (default) | benchmark, for performance changes
---
```

Then, in the body:

- **What and why**: the change and the problem, with the evidence (a failing test, a benchmark, a
  reproduction), plus review notes for whoever proposes it upstream.
- **Evaluation**: how it was measured against upstream, and the numbers.
- **Upstream**: what upstream would need to make the change unnecessary, and its status there.
- **Compatibility**: any behaviour that differs from upstream, or "none".

| Status | Meaning |
|---|---|
| `fork-only` | Carried here and nowhere else. |
| `proposed-upstream` | Raised upstream, by us or anyone else. Link it. |
| `upstreamed` | Upstream has it, or an equivalent. **Retire it.** |
| `superseded` | Upstream solved the same problem differently. **Retire it.** |

## Working on the stack

[`../maintaining.md`](maintaining.md) is the guide: the refs and what moves them, rebaselining onto upstream,
re-basing your own branches onto a new stack (`lake-stack rewire`), resolving a rebase that stops, and
editing, retiring and recovering changes. In short:

- **A new change**: one commit `lake(NNNN): title` with its record, squash-merged through a PR.
- **A fix to a change**: `fixup! lake(NNNN): title`, squash-merged; the next rebaseline folds it in.
- **Upstream moves**: nothing happens until the maintainer runs `lake-stack rebaseline`, which rebases,
  checks and tests the stack locally, stages it on `staging/<name>` for CI, and promotes it to `master`
  with `--push` only once that build is green, tagging the old head `lake/stack/<date>-<sha>` first.
- **Upstream takes a change**: the next rebaseline drops it, or reports it when only its record is left.
- **Change branches** `lake/change/NNNN-name` are upstream plus one change and its `depends_on`
  (transitively), without records, regenerated by each published rebaseline (`lake-stack branches`). Their diff against
  upstream is what an upstream pull request would contain. Never commit to one.

## Proposing upstream

Upstream does not accept AI-written issues, pull requests or comments, and blocks accounts that send
them. A person reads the record (its review notes say where to look hardest), reproduces the problem
on upstream, and opens the pull request by hand from the change branch. [upstreaming.md](upstreaming.md)
has the rest.

## Index

The records in this directory are the index, one per commit of the stack; `lake-stack status`
prints them in stack order with their status. There is deliberately no table here: this page belongs
to `lake(0001)`, and a list kept in it would make every change edit the bottom commit of the stack.
